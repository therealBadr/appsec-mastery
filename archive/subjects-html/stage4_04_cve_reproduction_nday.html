Foreword

"A CVE advisory tells you a vulnerability exists and roughly where. It does not hand you a working exploit — reconstructing one from the advisory, the patch diff, and your own analysis is where research actually happens."

Introduction

Why This Subject

Reproducing real, disclosed CVEs from scratch is deliberately positioned this late in the roadmap because it requires every prior skill at once: the vulnerability-class recognition from Stage 1-2, the code-review method from Secure Code Review, and — often — the memory-safety forensics from OS Internals if the CVE happens to be a memory-corruption bug rather than a web vulnerability.

Theory

What You Must Understand

Reading a security advisory

CVE entries, vendor advisories, and NVD records typically describe the vulnerability class and affected versions but deliberately omit exploitation detail — the research skill is inferring the likely vulnerable code path from the advisory's language plus the software's own source or patch history.

  • Advisory language is often precise if you know how to read it: "improper neutralization of special elements" is injection-class vocabulary; "out-of-bounds write" is a memory-corruption vocabulary
  • The affected-version range itself is a clue — narrowing exactly which release introduced or fixed the bug focuses your source investigation

Patch-diff analysis

The single highest-signal source for understanding a CVE precisely: the commit that fixed it, diffed against the vulnerable version, directly reveals what was wrong — reusing the differential code-review skill from Secure Code Review's capstone, now applied to a real historical fix instead of a synthetic one.

  • A patch diff that adds a bounds check, a parameterization, or an input-validation function tells you exactly what the vulnerable code was missing
  • Not every CVE has a public patch diff (some vendors don't use public version control) — in that case, advisory text and independent researcher writeups become the primary source instead

Building the reproduction environment

Standing up the exact vulnerable version in an isolated lab — often the most time-consuming part in practice, involving dependency archaeology and sometimes a container built specifically to pin an old, vulnerable software version.

  • Docker is usually the fastest path to a clean, disposable vulnerable-version environment, directly reusing your Inception-project Docker fluency
  • Isolation matters doubly here: you're deliberately running known-vulnerable software, so it must never be reachable from anywhere but your own lab network

Proof-of-concept construction and severity validation

Building a working exploit that demonstrates the CVE's claimed impact for real — closing the loop between "the advisory says this is critical" and your own independent verification, which is exactly the reachability/impact-validation discipline from SCA and SAST Engineering applied to one specific, real vulnerability.

  • A PoC that merely crashes the target confirms a bug exists but not necessarily the advisory's claimed severity (e.g. "remote code execution" claimed but your PoC only achieves denial of service) — the gap between the two is itself a finding worth documenting
  • Responsible practice: since the CVE is already public, publishing your own reproduction/PoC is normal and expected in the research community, but only for the disclosed version, never demonstrated against a live, patched production target
Chapter III

Practical Outputs

Practical Outputs
  • A full reproduction of at least 3 real CVEs (a mix of web-application and, if feasible, one memory-corruption CVE reusing OS Internals' skills) from advisory to working proof-of-concept, each in an isolated lab.
  • A written analysis per CVE: the advisory's claims, your patch-diff (or independent) analysis of the actual root cause, your reproduction environment setup, and your PoC with its actual demonstrated impact compared against the advisory's claimed severity.
  • At least one case where your independent analysis meaningfully refined or corrected the public understanding (e.g. the actual required preconditions are narrower than the advisory implies, or the real-world exploitability is lower/higher than the CVSS score suggests) — a genuine, if small, research contribution.
  • A public writeup of your reproduction work (GitHub or a blog) written to educate, not just to prove completion — this is the roadmap's explicit Stage 4 exit-gate deliverable: "5 real CVEs reproduced from scratch with full writeups."
Chapter IV

Common Delusions

Common Delusions at This Stage
  • "If there's no public PoC, it can't really be that serious." Absence of a public PoC often just means nobody's published one yet, or the vendor asked researchers to hold it — advisory severity and PoC availability are independent facts.
  • "Reproducing someone else's finding isn't real research." Independent reproduction is a genuine, valued skill distinct from original discovery — it validates (or corrects) the public record and builds exactly the technique original research later depends on.
  • "A CVSS score is ground truth." As with pentest reporting, CVSS is a starting estimate — your own reproduction is what actually establishes ground truth for a specific environment.
Chapter V

Exit Gate

Exit Gate — must do all of this without notes
  • Given a real CVE advisory you haven't seen before, identify the likely vulnerability class and code area from the advisory text alone.
  • Walk through a patch diff for a real CVE and explain precisely what the vulnerable code was missing.
  • Demonstrate a working reproduction of one of your researched CVEs, live, in your isolated lab.
  • Defend a case where your own analysis diverged from the advisory's or CVSS score's claims, with evidence.
